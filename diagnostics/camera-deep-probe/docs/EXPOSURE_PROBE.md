# FilmProbe：实机曝光与接口探针

这是独立的 `FilmProbe.3dsx`，与 Film3DS 共存。它直接调用 CAM 服务，不经过
`film_camera_open()`，避免主程序因为某个 AE 初始化结果不符合预期就提前退出。
它不会把返回成功当作曝光控制成功，也不会给未标定的增益编造 ISO 数字。

## 构建和启动

安装 devkitPro 的 `3ds-dev` 后，在仓库根目录：

```sh
make -f Makefile.probe
```

不依赖 Citro2D、JPEG、LUT 或 Film3DS 的图形界面。CI 的 `Film3DS-ARM11`
产物包含 `FilmProbe.3dsx` 与对应 SHA-256。

把 `FilmProbe.3dsx` 放入 SD 卡的 `/3ds/`，通过 Homebrew Launcher 打开。

- **A**：测试公开接口，并读取已识别传感器的寄存器。
- **X**：在上述测试后，增加积分时间、模拟增益、MCU 自动曝光目标的直接写入试验。
- **Y**：切换每个阶段的最后一帧保存为完整 YUYV；默认保存完整分辨率的 PGM 亮度图。
- **B**：停止当前试验；已开始的直接写入仍执行恢复。
- **START**：在菜单或结果页退出。

也可用 `3dslink FilmProbe.3dsx --auto --direct --raw` 启动无人值守运行。
`--auto` 必须显式传入才会跳过菜单。三颗相机依次测试，整个流程可能超过十分钟，
具体取决于帧率、SD 卡与 I²C 访问耗时；顶部显示当前传感器和阶段。

固定机器、保持照明和场景不变，给所有镜头安排有暗部、中间调和亮部的画面，避免全黑或全白。
PGM 模式每次完整运行预留约 64 MB，完整 YUYV 模式预留约 128 MB；日志另占空间。
探针没有自动判断环境照度是否恒定的能力。

## 具体测什么

每颗相机独立初始化，记录每个调用的原始 `Result`。一个镜头失败仍尝试下一个；
寄存器读取被拒绝时仍测试高层接口。只有芯片 ID 成功读出 `0x2280`，才启用
MT9V113 寄存器地址表；未知型号保留 ID 和 API 结果，直接写入跳过。

| 试验 | 保存的证据 |
| --- | --- |
| CAM 初始化、选择、VGA、YUV、Context A、传输设置 | 每项调用与返回码，不把后续采集错误覆盖设置结果 |
| 相机选择、睡眠状态、Y2R 系数、工厂与立体标定读取 | 原始返回码及可用字段；立体视角不是光圈 |
| AE 开／关，分别测试曝光 `-5…+5` | 交错的 `0 → 目标档 → 0` 参考阶段，预览和硬件状态 |
| 15、30、15→5 FPS，以及五种拍摄模式 | 时序、积分时间、增益、亮度变化 |
| 全画面／中央 AE 测光窗 | API 是否接受及传感器和画面的变化 |
| 直接缩短粗积分时间 | 写入、即时回读、丢弃八帧后逐帧回读、恢复再采样，两次循环 |
| 直接降低四通道模拟增益的初始增益字段 | 保留数字增益及其他模拟增益位；同样做两次修改／恢复循环 |
| 直接降低内部 MCU 的 AE_TARGET | 使用字节逻辑地址 `0xA206`；保存与恢复目标值，两次循环 |

每阶段先记录即时状态，采集八帧供设置生效，再记录十二帧。
每个测量帧接收前后分别读取寄存器，并记录时间、完整帧 CRC32、亮度均值、中位数及端点计数。
`endpoint_low/high` 只计数 0/16 与 235/255 两组代码，不等于已经确定的剪切像素比例。
接收耗时包含主机处理与调度，不能当作快门时间。

读取包括 PLL、行长、帧长、粗／细积分、模拟增益代码、通道组合增益、传感器及 IFP
数字增益，以及 MCU 的 AE 目标、状态、积分和虚拟增益。逐帧读数会影响吞吐量，
且不是原子化的帧元数据；接收前后分开记录，供分析竞争和延迟。

直接写入仅限 `0x3012`、`0x3056/58/5A/5C`、MCU `0xA206`。
AE／AWB 关闭状态、基准图像和需要保存的寄存器读取必须先成功；
写入部分失败、按 B 或采集超时仍尝试恢复全部目标寄存器，恢复回读失败就停止后续试验。
恢复后的连续帧也保留，供检测固件延迟覆盖。没有写入 OTP、PLL、电源、复位、保留位或任意地址的入口。

## 取回结果

每次运行创建独立目录，已有目录不覆盖：

```text
/3ds/Film3DS/probes/run-时间戳-序号/
    manifest.txt
    calls.csv
    reads.csv
    frames.csv
    s1-p001-阶段名.pgm
    ...
```

复制整个目录到电脑，运行：

```sh
python3 tools/exposure_report.py /path/to/run-folder
```

生成 `analysis.json`，包含每颗相机的接口接受／拒绝情况、失败地址和返回码、
各曝光档位对应的物理寄存器变化、逐阶段数据、每次直接写入的分层结论。
没有结束标记时仍可分析完整的 CSV 行，结果标记为不完整；截断行报错，原始日志仍保留。

结论依次区分：写入失败／部分失败、API 接受但回读不符、即时回读成功但未保持、
恢复未确认、寄存器控制得到观察但画面证据不足、寄存器及画面响应均得到观察。
最后一种还要求修改和恢复阶段有完整十二帧、其他受监测曝光参数保持一致、
亮度发生变化并在恢复后回到基准附近。曝光目标试验通常会改变其他曝光参数，
因此不会被当作独立快门／增益控制证明。

单次无响应可能来自饱和、参数写保护、内部自动控制覆盖或场景条件；报告不擅自选定原因。
`constant_in_sample` 只表示采样窗口内观测值不变，不证明换一个照度后仍锁定。

## 当前边界和验证状态

- 探测的是当前 Homebrew 运行环境下的 `cam:u`，不能据此声称所有权限级别都禁止某项功能。
- 没有尝试绕过权限、特权服务、任意地址遍历或传感器 RAW 接收；YUYV 是相机处理后的数据。
- 尚无可靠的镜头 F 值；不从标定视角反推出光圈。
- 未把 PLL 和时序换算为曝光秒数，也未标定 ISO；完整原始值留待硬件数据验证后解释。
- 主机测试会注入接口拒绝、写入被忽略、延迟覆盖、恢复漂移、部分帧、读取失败和其他增益变化。
  C 测试执行实际试验／清理函数，验证中止和采集超时仍恢复、未知型号不写入以及 OTP 地址被拒绝。
- 主机测试与 ARM11 构建均不等于实机已测通。必须取得本机导出的数据，才能判断可用控制路径。

原始参考：[libctru CAM 声明](https://github.com/devkitPro/libctru/blob/master/libctru/include/3ds/services/cam.h)、
[IPC 实现](https://github.com/devkitPro/libctru/blob/master/libctru/source/services/cam.c)、
[GBATEK 的 SYSCTL／CORE／AE 地址表](https://mgba-emu.github.io/gbatek/)、
[MT9V113 厂商数据手册镜像](https://datasheets.su/DS/OnSemi/MT9V113-D.pdf)。
地址表主要由 DSi 逆向得到，3DS 型号关联来自芯片 ID 记录；探针会在实际机器上重新验证。

## 深入探测版本（5a1e62d-deep2）

本地增强版先读取 Luma 版本与 camera/i2c 的进程、段地址和内存映射，
只将这两个进程的可读非 MMIO 普通内存映射到探针进程，写出原始文件后立即解除映射。
每个进程每份快照最多 16 MiB；文件长度和映射失败均记录，动态数据不是原子快照。
此路径不写入驱动进程、不修改驱动、不修改 NAND。
参考固定到 Luma3DS `1441535d222002353b79d290b6200ceab2e32cb0` 的
`k11_extension/source/svc/GetProcessInfo.c`、`MapProcessMemoryEx.c` 和 Rosalina `csvc.s`。

`cam:u`、`cam:c`、`cam:s` 分别请求只读 ID 和 AE 状态；仅 ID 确认为 0x2280 后，
已有的寄存器写入白名单才可通过识别出的服务路径执行。未知型号仍不写入。
IPC 日志保留服务传输结果、命令结果、请求和完整 64 字响应缓存；其中响应头长度之外的字不当作有效载荷。
布尔返回值按 8 位解码，且要求响应命令与字段数量正确。用不同输出缓存初值做只读比较。

采集先测试四帧连续接收。如果失败，明确另测四帧“每帧停止/清缓冲后重新启动”，
其结果记为 `single_frame_restart`，不能证明连续取流时曝光锁定。
两种方式都失败则停止该镜头扫描，保留证据并继续下一镜头。
每阶段仍需完整的 8 帧等待和 12 帧测量。等待事件结果单独记录。
主机报告区分流程结束与采样完整，旧版只有 END complete=1 的日志不会再报告完整成功。

主机执行（掌机先进入 NetLoader）：

```sh
python3 tools/run_deep_probe.py 192.168.0.55 FilmProbe.3dsx --out /path/to/new-run
```

启动驱动导出后、每颗镜头结束后和最终结束后分别回传，接收端保留独立目录与 SHA-256。
SD 原件仍保留。分析最终目录：

```sh
python3 tools/driver_report.py /path/to/new-run/final
python3 tools/exposure_report.py /path/to/new-run/final
```

新增故障检查覆盖非零响应高位、缺失字段、错误响应命令、连续采集失败后的显式
单帧比较、两种采集均失败以及流程结束不能代替完整测量。

### 实机发现与撤回的诊断路径

实机 `deep2` 已在三颗相机通过 `cam:c` 读到 0x2280 和曝光相关寄存器；
`cam:u`/`cam:s` 对相同芯片 ID 读取返回 0xD8A053EA。
布尔响应含高位残留，正常状态应按低字节解释。

`deep3` 在首个检查点回传前发生 i2c 系统模块的 ARM11 Data Abort（permission-page）。
转储已离线解析：PC=0x001018F0，`str r1,[r2]`，FAR/R2=0x00102660，
DFSR=0x80F（写入时页面权限错误）。更早的指针破坏来源尚未确定，不能归因于原驱动本身。
从 `deep4` 起撤回跨进程驱动内存映射/导出，源代码不再包含该实现；
保留已导出的驱动文件供离线分析。启动只通过文件系统复制用户报告的
`/luma/dumps/arm11/crash_dump_00000008.dmp`（同时检查 `.dump` 扩展名），
原件保留，随后回传 startup 检查点。

等待接收必须实际返回 0 才算完成；正值 0x09401BFE 是超时，不能用
R_SUCCEEDED 把它当作收到帧。停止生产者后最多等待 2 秒 IsBusy 变为 false，
未确认停止则禁止复用 DMA。先布置接收缓冲再启动生产者。
寄存器前后快照采用显式逐帧启动/停止，避免读寄存器阻塞期间发生无接收缓冲的溢出；
该模式不替代连续预览曝光保持测试。

接收器为完整原始 IPC 日志允许 `ipc.csv` 最大 512 MiB，其余单文件维持 100 MB 上限。
检查点最长等待 2 小时；`--receive-only` 可在掌机继续运行时恢复主机监听，
会核对目标 IP 和已部署二进制 SHA-256，不重新部署，不覆盖已收到的检查点。

### 显式补测范围（deep5）

`probe_plan.h` 集中定义请求：默认三颗、从第 3 测量阶段开始；
`--sensor=1..3 --from-phase=3..58` 仅选择一颗并重建之前的设置，
之前的阶段标记为 SETUP_REPLAY，既不捕获也不计入完成数。
为保留直接控制修改/恢复成对执行，禁止从直接测试中途开始；未知参数或无效范围拒绝启动。
当前补测请求为第三颗从第 34 阶段起，预期 39 阶段、468 个有效测量帧。
单独保留两份来源，不将跨运行的记录伪装成一次连续采样。

第五版只在所有测量和文件关闭后初始化一次网络并回传 final 检查点，
不在运行中反复销毁和重建 socket 服务。原始 SD 文件继续保留。
如果回传失败，可用现成 ftpd 启动后运行 `tools/retrieve_probe_ftp.py` 只读回收。

主机补测命令：

```sh
python3 tools/run_deep_probe.py 192.168.0.55 FilmProbe.3dsx --sensor 3 --from-phase 34 --out /path/to/new-continuation
```

完整性报告按 REQUEST 的相机/阶段范围逐项检查真实 frame 8..19 和寄存器读数，
流程结束字符串不能替代数据。原始中止记录始终保留。

### 无线中断后的只读文件回收

实机 FTP 曾报告无线接口未配置，随后失去连接。大文件不重新运行测量获取。
`retrieve_probe_ftp.py --run run-... --chunk-bytes 262144` 显式启用分段读取：
先下载清单、帧记录和寄存器记录；每个片段单独建立只读 FTP 会话，使用 REST 指定偏移。
中断立即返回错误，不自动重试；已有 `.partial` 保留。下一次明确执行时校验来源目录、
长度和已有片段首尾后续传。完整文件才重命名，并记录长度和本地 SHA-256；
全部文件完成后才生成 `received-sha256.json`。本地哈希证明下载后文件未被修改，
FTP 不提供设备端哈希，因此不将其描述为设备端与主机的哈希比对。

`python3 tests/ftp_segments.py` 用真实本地控制/数据套接字检查有界读取、REST 偏移、
截断数据保留及仅使用只读命令。分段回收不修改原始文件、探针采样范围或主应用。

### SD 压缩回收入口

`FilmRecovery.3dsx --run=run-<digits>-<digits>` 是单独的文件回收入口。
它不初始化 camera/I2C，不访问进程内存，也不创建任何测量工作。
仅从明确指定的已结束 probe 目录读取登记扩展名的普通文件，
将 tar.gz 写入独立的 `sdmc:/3ds/Film3DS/recovery/`，保留原件。
同名压缩包存在时拒绝重新打包；`--serve-existing` 显式复用并先验证已有 gzip 尾部校验，
避免重传程序后重复压缩或依赖 SD 文件系统的覆盖 rename 行为。
压缩包包含设备端逐文件长度与 CRC32 索引；压缩成功后才开放只读 HTTP 5000。
仅允许 `/info` 和 `/archive`，单次 Range 上限 256 KiB，不开放任意文件路径。
PC 主动连接设备，无需 PC 接收掌机发起的入站连接。

`tools/retrieve_probe_archive.py` 保留断点，核对设备端压缩包长度/CRC32、
gzip 尾部校验、tar 索引覆盖及每个解压文件的设备端长度/CRC32；
已存在的原始文件必须完全一致才能复用。全部通过后才写出完整接收清单。
网络异常不自动重试，不把不完整文件作为完成证据。
若压缩包已生成但回收服务退出，可启动现成 ftpd，使用
`tools/retrieve_probe_archive.py IP --ftp-run run-... --out DIR` 读取同一压缩包。
FTP 425 等临时数据通道错误会停止本次命令，已收到的断点保留；
再次明确执行时继续，完整接收后仍须通过 gzip 和设备端逐文件 CRC。

验证：`python3 tests/probe_recovery.py` 运行真实 C 打包器/HTTP 服务端与 Python 客户端，
覆盖断点下载、CRC 错误拒绝、Range/路径越界拒绝和原件保留；
`make -f Makefile.recovery` 与 `tools/verify_3dsx.py FilmRecovery.3dsx` 验证掌机二进制。

### 独立标定入口 calibration-1

`--auto --calibrate --sensor=1..3` 显式选择一个传感器；拒绝与旧 direct 或补测参数混用。
不改变主应用。`calibration_contract.h` 注册 seed/normalize/integration/analog/digital/restore
及对应写入掩码，未知类型拒绝。继续沿用寄存器白名单，不写 PLL、OTP、复位或保留地址。

主范围 54 阶段：30/15/5 fps 各自自动测光参考、关闭 AE/AWB 且读回 MCU 确认后，
数字增益归一、模拟通道比例保留、积分代码 1/4/16/64/帧长四分之一/四分之三的 A-B-A；
15 fps 下再测模拟 0.5/1/2/4 倍、数字乘数 2/4 的独立修改与恢复。
最后 4 阶段：30/5 fps 的 16 位粗积分边界 65535 及恢复。总计 58 阶段（phase 3..60）。
边界点等待 1 帧测量 3 帧，接收/停止上限 30 秒；其余等待 8 帧测量 12 帧。
拒绝的边界点保留为失败；只有恢复已完整采样、相机静止可复用时才进入下一边界试验。
失败不计入成功阶段，不通过隐藏重试补齐。有限寄存器边界不构成 B 门或真实秒数证明。

每个固定帧率另采 24 次紧凑 DMA 事件时间戳，期间不写 CSV 或读取曝光寄存器；
突发记录与逐帧曝光采样分别判定，失败不会冒充连续预览稳定。
roi.csv 保存中央区域和九宫格统计；noise.csv 为处理后 Y 输出的逐像素时域方差，
不能称作 RAW 电子读出噪声。下屏显示原生 4:3 采样图，固定目标视场。

每个阶段在写入前登记 calibration_plan.csv，保存预期五个控制寄存器、类型、帧数与参考阶段。
中止、失败、未知读回均尝试恢复，并记录结果。边界全部成功时为 678 个有效测量帧。
结束关闭文件与相机后只打包一次并开放只读 HTTP 5000，由 PC 主动下载。
`run_calibration_probe.py` 明示 30 秒一次、最多 2 小时的服务就绪轮询，不重部署或重跑采样；
数据下载异常立即退出，原始文件与断点保留。

calibration-1 最初两次实机在正式控制写入前意外退出，原件分别保留在 collection-01/02。

### storage-check-1 与离线采样

卡拷贝核验确认 smoke 仍不完整；用户报告的原始 FS 错误为 0xC960454B。
不再将退出预设为 CPU 崩溃、磁场或 Wi-Fi 问题。独立 FilmStorageCheck 入口只在
`storage-checks/run-...` 新目录创建 10 个 256 KiB 文件，交错写入、flush/fsync、重开读回 CRC32。
写失败、截断、额外字节或 CRC 不符立即失败，不重试、不覆盖或删除原件，不启动相机或网络。
该有限负载通过不构成整张介质健康认证；失败时不继续相机标定。
`tests/storage_check.py` 实际运行 C 诊断，覆盖独立目录/原件保留、写故障和读回篡改拒绝。

也不能把未完成数据声明为成功。配合 smoke 可先验证 20 帧再进入完整标定。

`make -f Makefile.offline` 生成独立 HBL 入口 FilmCalibration：无附加参数时显式选择
Sensor 1、SD-only、手动启动，A 选20帧短测，X选58阶段整轮；开始前不创建测量工作。
标准 FilmProbe 默认行为保持。数据可结束后用 FTP 回收，并非要求拔卡。

FTP 连续大文件曾超时，快速分段新建控制会话又遇425。新增 `--persistent --chunk-bytes 16384`：
同一控制会话进行有界 RETR，再以 ABOR/NOOP 显式同步回应；只接受226/225及明确的
Transfer aborted回应，不吞掉其他425错误。完整片段且控制流恢复同步后才提交到本地断点。

完整计划在 phase 33 遇到 SD 写入错误后，不重复已验证的 phase 3–32。
`calibration_scope.h` 先注册独立 scope，再由同一诊断入口执行：

|---|---:|---:|---|
| `gain` | 14 | 168 | 15 fps 基准、0.5/1/2/4×模拟增益、2/4×数字倍率，逐点恢复 |
| `slow` | 14 | 168 | 5 fps 基准、六个积分代码，逐点恢复 |
| `limits` | 8 | 78 | 30/5 fps 各自自动基准、归一化、65535有限积分边界及恢复 |
| `digital` | 6 | 72 | 单独补测15 fps下2/4×数字倍率，各有基准及恢复，不再执行被拒绝的模拟增益点 |
| `codes-fine` | 14 | 168 | 原始0210/0218/0220/0228/0230/023C代码响应，不宣称倍率 |

每段必须显式指定 `--calibrate --offline --sensor=N`，拒绝未知段、重复段、smoke、
direct 或非默认 from-phase 混用。各段本地 phase 从3开始，不宣称继承上一轮曝光状态；
每段重新初始化并验证 AE/AWB 锁定。limits 的基准写入失败也必须尝试恢复原控制。
有限边界不构成 B 门证明。58阶段原合同仍保持 calibration-1，不把分段冒充整轮。

分段采用显式 `LOG_POLICY frame_boundary buffers=32768 all_streams=1 retry=none`：
仍保存全部 CSV 与原始 request_first8/response64，不增设后台队列或重试；
标准 stdio 使用32KiB缓冲，在帧结束、控制阶段和退出检查点统一刷新。
原始 ipc.csv 现在也纳入流错误检查，任一日志流失败即停止测量；不能保证修复介质故障。
主机报告核对 scope、阶段数、类别、逐帧证据和该 scope 的 DMA burst，未知或越界证据拒绝。

验证：`make probe-test`、`python3 tests/calibration_report.py`、
`make -f Makefile.probe`、`python3 tools/verify_3dsx.py FilmProbe.3dsx`。
实际 C 测试覆盖三段完整计划、失败恢复、真实 `/dev/full` 写失败停测；报告负例覆盖缺帧与未知 scope。
本次边界为 Film3DS 独立硬件诊断；未修改主应用、原驱动、Vision-product 的
CONTRACT_MATRIX/验证器/运行时内部字段，不涉及 RegionTask 或 LaneAdmission。

实机 gain 段显示 nominal2× 读回保持但画面反而变暗，nominal4× 的蓝通道03CF读回02CF。
因此参考公式只是待检验模型，不能作为真实增益或ISO。新增原始代码实验：独立 seed 后
把积分缩短到 seed 的八分之一（至少1），四通道统一0220作为固定基准，保留数字倍率1；
显式 `code_baseline` 只允许mask31（3012和四增益），`code` 只允许mask30（四增益）。
逐代码后都采样验证恢复。只有恢复完成、相机就绪且没有I/O/取消，才允许下一个独立代码；
不是重试被拒绝代码。拒绝或失败的目标永远保留为不完整测量，即使扫描执行到末尾。
`CODE_POINT`/`CODE_SCAN` 分别记录目标采样、恢复和尝试数量，最终还要恢复seed控制。
真实C负例模拟bit8写入被清除：仍跑完6个独立点、每点恢复，报告准确标出两个不完整点，
不把“所有点尝试过”冒充“所有点测量通过”。

digital实机段完整通过，但原场景的4×中心高亮阈值比例为1，不能用饱和样本比较噪声。
digital-headroom使用显式code_baseline/mask31，保留原通道比例并缩短积分，固定其余设置；
它仍记录实际裁切比例，不能预设较短曝光必然不饱和。原有过曝原件继续保留。

### ram-evidence-1：绕过采样中的SD写入

limits首次实机连预检PGM都只写入47104/307215字节，未进入正式测量。
显式`--ram`必须与单sensor calibration/offline、smoke或已注册part配合；
拒绝full58、raw、direct、resume及未知范围，不启动未注册工作。
`ram_log.h`注册20MiB固定arena和每类文件容量，实际FILE写回调有界，失败立即记录并停测；
没有SD退路、清理旧文件、后台队列、淘汰、压缩或采样重试。
测量日志、原始IPC、PGM和测量期间APT事件写入RAM；旧转储不再复制。
RAM模式致命异常仍显示寄存器并停留，不恢复执行，也不写SD；断电会丢失RAM。

相机关闭、所有测量流关闭后才冻结数据并计算每文件CRC32；冻结后不再追加证据。
随后开放HTTP5000的只读`/info`与带有界Range的`/file/N`，不允许路径、写入或任务创建。
客端断开不会清空快照；网络故障不触发重测。START明确丢弃RAM并退出。
`tools/retrieve_probe_ram.py`先验证索引和范围，再按CRC核对整文件并记录本地SHA-256；
断点必须与同一冻结索引及首尾片段匹配，不自动重试失败请求。

Linux验证命令另含`python3 tests/ram_evidence.py`：真实fopencookie、真实TCP端点、
CRC、容量不足、冻结后写入拒绝、无效文件/范围、空文件、同快照接续。
实际C相机测试还用RAM完成72帧并通过严格报告。macOS不提供fopencookie，
上述C验证在既有Linux构建容器中执行；3DS新libc原生构建和3DSX校验通过后才上传。

RAM实机验证发现直接close会丢失排队的HTTP正文。发送后使用SHUT_WR，并有界等待
客端消费Content-Length并关闭，再释放socket；不重发请求或采样。真实TCP_CORK+
abortive-close测试通过，第二次RAM短测13份原件的原生CRC/长度/本地SHA及12正式帧实机通过。

FFFF长积分段原始IPC为传输成功、服务C9602FEF、输出FFFF；保存的原驱动
0x0010A64C–65A明确将FFFF当错误哨兵。失败仍拒绝，新增limits-fffe只换独立输入值，
不绕过校验、不改驱动。该段逐帧报告还拒绝两次恢复的控制漂移；边界seed后不再

任何漂移拒绝该点；只有重新采样验证的恢复可允许下一独立点。真实C负例在等待帧后
