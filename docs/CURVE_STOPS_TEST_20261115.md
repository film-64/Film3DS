# 曲線檔位測試：確認存在幅度與作用範圍問題

## 結論

**目前確實有曲線設計問題，不能只歸因於相機寬容度。**
UI 的 -5…+5 已正確進入計算，方向也正確；但數學設計讓高光在接近純白時迅速失效，
陰影在接近純黑及超過特定亮度後失效。前置曲線再經 LUT 的 shoulder/toe 壓縮，
會使部分相鄰檔位的最終 RGB 完全相同。先前的單調性／存檔測試沒有檢查
「每一檔的實際幅度、區域覆蓋與最終可區分性」，不足以證明效果合格。

本輪只增加離線測試與報告，沒有更改產品曲線、重新編譯部署包或操作相機。

## 測試對象與方法

- 使用已部署的凍結版本 `build/darkroom-offline-20261115-r1`，3DSX SHA-256：
  `e6c6c91ba7e7a9fb2fce1665f9f057189719ae1c8c445b7f2ba2bf583f81502a`。
- 驗證 package manifest 全部檔案雜湊；當前 color/image/ui/darkroom 核心與凍結版本一致。
- 以新測試驅動連結**凍結版實際 C 核心**，透過 `film_darkroom_adjust` 設定每一檔，
  使用 `film_develop_grade_pixel` 與 `film_develop` 計算，不用 Python 重寫一套曲線作替代。
- 4 種情況：無 LUT、Portra 400/Endura、Gold 200/Endura、Classic Chrome。
- H/M/S 各獨立測 -5…+5；其他曲線為 0，曝光為 0，關閉顆粒、銳化、縮放、舊修正。
- 256 階完整中性灰階，每一點記錄 LUT 前、LUT 後浮點結果及最終 8-bit 量化；
  共 `4 × 3 × 11 × 256 = 33,792` 組點測量。
- 另使用本地留存的 `ROLL0067.F3S`（640×480、Sensor1、YUYV、檔內 Rec.709 full-range），
  完整沖洗 132 張逐檔影像。這是歷史本地樣本，**不是此次機上正在顯示的畫面**。
- 不經 JPEG，直接保存實際 RGB24 輸出，避免把 JPEG 壓縮差異誤當曲線效果。
  未套用 SD 上可能存在的 camera RGB matrix，沒有測量真實螢幕亮度。

浮點「碼值」指 sRGB R/G/B 按 .2126/.7152/.0722 加權後乘 255；這是便於比較輸出變化的
數值，不是感知亮度或線性光亮度。報告另保留線性 Y 以檢查單調性。
整數檔位數則按**完整 RGB 三通道**去重，並非只看加權值是否相等。

## 1. 高光：越接近白點，調整越小

下表是同一灰階輸入，高光由 -5 到 +5 的**整段總差**，不是單檔差。

| 輸入灰階碼值 | 無 LUT 總差 | Portra 總差 | Portra 十一檔的不同 RGB8 結果數 |
| --- | ---: | ---: | ---: |
| 211 | 34.59 | 14.33 | 見完整 CSV |
| 240 | 10.72 | 2.33 | 見完整 CSV |
| 248 | 4.89 | 0.91 | 4 |
| 254 | 0.69 | 0.12 | 1 |
| 255 | 0 | 0 | 1 |

輸入 254 尚不是純白，十一檔卻已得到相同的量化 RGB；輸入 255 更是數學上完全不改變。
在高光區 192…254，Portra 相鄰檔浮點變化有 **59.52% 小於一個碼值**，
**20.79% 的相鄰檔對得到完全相同的 RGB8**。
Gold 的比例分別為 59.68%／20.32%，Classic Chrome 為 59.21%／36.03%。

因此這不是 UI 沒接到檔位，而是曲線有效幅度與 LUT 後的量化結果不足。

## 2. 陰影：深黑被 LUT toe 進一步壓縮

| 輸入灰階碼值 | 無 LUT 的 -5…+5 總差 | Portra 總差 | Portra 不同 RGB8 結果數 |
| --- | ---: | ---: | ---: |
| 0 | 0 | 0 | 1 |
| 8 | 7.90 | 0.33 | 1 |
| 16 | 12.99 | 1.26 | 3 |
| 32 | 20.02 | 6.81 | 見完整 CSV |
| 56 | 30.45 | 28.15 | 11 |
| 118 | 0 | 0 | 1 |

所以陰影不是整段都沒效果：在約 56 的位置相當明顯，但深黑處的很多檔位無法區分，
到了約 118 又完全沒有作用。陰影區 1…63，Portra 有 **34.92% 的相鄰檔對 RGB8 完全相同**，
Gold 為 33.49%。同一張圖裡，不同亮度位置對「一檔」的反應很不均勻。

## 3. 根因在目前採用的錨點

目前線性光錨點固定為 `0/.04/.18/.65/1`：

- S 只移動 `.04`（約 sRGB 56）；在 `.18`（約 sRGB 118）恢復為零影響。
- M 只移動 `.18`；幅度上限為線性亮度 ±.035。
- H 只移動 `.65`（約 sRGB 211）；在 `1`（sRGB 255）強制恢復為零影響。
- 黑、白端點都釘死，所以高光最亮處與陰影最暗處的調整先天受限。
- 這是一組局部錨點偏移，尚不足以形成覆蓋合理、幅度可感知的高光 shoulder／陰影 toe 控制。
- LUT 在曲線之後再次改變明暗斜率，會進一步縮小某些區域的差異；此次測量明確重現。

各組灰階檔位方向檢查與亮度單調性均無反轉。這只能證明沒有倒序，不能證明幅度適合操作。

## 4. 留存照片的實際輸出

ROLL0067 解碼後約 28.10% 是暗部（加權碼值 <64）、56.87% 是中間區、15.03% 是高光（≥192）。
≥240 的極亮區只有 21 像素；原始 Y 平面沒有 255，約 0.50% 的 Y 為 0。
解碼 RGB 沒有三通道全白，約 0.39% 為全黑。這不是一張被整體白色裁切主導的樣本。

Portra 下，各相關區域相對 0 檔的平均輸出變化：

| 控制／區域 | -5 | -1 | +1 | +5 |
| --- | ---: | ---: | ---: | ---: |
| H／高光 ≥192 | -7.82 | -1.34 | +1.22 | +5.33 |
| S／暗部 <64 | +5.94 | +1.13 | -1.11 | -5.14 |
| M／中間區 64…191 | -7.50 | -1.43 | +1.40 | +6.64 |

此樣本有些區域的極端檔可看出差異，單檔仍多為約一個碼值。整張圖的 H +5 平均變化僅 +2.86，
因為它只影響部分區域。不能把「局部效果」與「全畫面曝光」當成同一件事。

## 寬容度與下一步

已被 ISP／8-bit 編碼裁切成相同值的紋理，後製不能憑空恢復。但此次**沒有相機、沒有輸入裁切的完整灰階測試**
同樣出現失效與檔位重合，因此目前曲線設計與 LUT 壓縮是已證實的原因，感測器寬容度不是充分解釋。
這份 F3S 也不足以測出感測器的實際動態範圍，不能據此宣稱相機只有多少 stops。

後續修正應先重新定義 H/S 的作用區域、肩部／趾部與端點行為，並明定使用者曲線與 LUT 明暗的優先關係。
不能只把 ±.12／±.02 係數任意放大，也不能再只以「單調」作驗收。修正後應重跑本批測試，
同時比較檔間幅度、受影響比例、重合檔位、裁切、色偏與真實畫面，而非先歸咎於硬體。
